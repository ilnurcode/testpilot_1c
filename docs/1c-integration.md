# Подключение реальной 1С — следующая стадия

Сейчас работают собственные Python-алгоритмы на нормализованном JSON. Пользователь сообщил о наличии тестовой базы с веб-клиентом и OData, но адреса и учётные данные для подключения ещё не предоставлены. Подтверждённого доступа из этой среды, реальных XML/EDT-выгрузок и запущенных Vanessa Automation / BSL Language Server пока нет. Совместимость с их форматами не заявляется. Методам неподдерживаемых адаптеров соответствует явный NotImplementedError.

1. Получить разрешённую обезличенную выгрузку двух версий одной конфигурации и точную версию платформы/EDT. Согласовать стабильный ID и правила переименования/удаления. Зафиксировать лицензионный доступ к инструментам.
2. Реализовать `ConfigurationAdapter.parse(bytes)->Configuration` на проверенных образцах. Для XML запретить DTD/внешние сущности, ограничить размеры и вложенность. Не выполнять код модулей. Сверить эталонные узлы/связи с экспертом в EDT.
3. Получить образец результата конкретной версии BSL Language Server. Реализовать `ProgramDependenciesAdapter.extract(modules)->list[Edge]`: соответствие символов object_id, тип связи, source/target, origin и confidence. Проверить вызовы, динамические случаи, циклы и недостающие модули. Динамические связи не объявлять доказанными.
4. Загрузить реальный каталог тестов с теми же object_id, экспертно подтвердить привязки и совместимость версий. Импортировать обезличенную историю, отделив её от synthetic; откалибровать веса, время и ML-порог на временной отложенной выборке.
5. Развернуть отдельный исполнитель в разрешённой среде 1С/Vanessa. Согласовать аутентификацию и защищённые endpoints; секреты передавать через среду/менеджер секретов. Никогда не включать команды изменения конфигурации из недоверенного JSON.
6. Исполнитель получает `POST /api/v1/plans/{id}/execution-jobs` после экспертного подтверждения. Контракт содержит ID задания/плана, конфигурацию, версию, тесты и параметры. Сам MVP ничего не запускает.
7. Реальный runner отправляет `POST /api/v1/execution-results`: execution_job_id плюс run со всеми ожидаемыми test_id, временными метками, status, duration_seconds, error и HTTPS-ссылками на артефакты. Неизвестные/недостающие ID и несовместимые версии отклоняются, повтор идентичен — идемпотентен, изменение зафиксированного отчёта — 409. Ссылки сохраняются как строки, сервис их не скачивает.
8. Проверить на живой стендовой базе полный цикл, ошибки/таймауты, права, резервное копирование и согласованные нагрузочные ориентиры. Только после этого утверждать совместимость и качество интеграции.

Контракты: `contracts/execution-job-1.0.schema.json`, `execution-report-1.0.schema.json`, `test-run-1.0.schema.json`. Поле `executor_connected=false` остаётся честным статусом данного MVP даже после импорта вручную присланного отчёта.

Уточнённый целевой процесс с расширениями и Playwright — [connected-workflow.md](connected-workflow.md). Добавленная CLI-диагностика `python -m testpilot.integration.probe` проверяет только публикацию; она ещё не является исполнителем тестов.


## Реализованные адаптеры интеграции (Фазы 1-3)

В кодовой базе добавлены ключевые модули сопряжения с 1С:
1. `testpilot.impact.xml_adapter.XMLEdtAdapter`: безопасный разбор XML/EDT выгрузок метаданных 1С (`.xml` и `.zip`), защита от XXE/DOCTYPE, извлечение объектов (`Catalog`, `Document`, `InformationRegister`, `AccumulationRegister`, `CommonModule`, `EventSubscription`) и связей по реквизитам в нормализованную модель `Configuration` 1.0.
2. `testpilot.integration.odata.ODataClient`: клиент OData 1С (чтение `$metadata`, выборка сущностей с `$filter`/`$select`, создание, изменение и удаление тестовых записей, белый список таблиц `ALLOWED_PREFIXES`, CLI `python -m testpilot.integration.odata`).
   При автозапуске OData-сценария HTTP 404 для указанной сущности даёт статус `failed`; доступность `$metadata` не заменяет проверку этой сущности.
3. `testpilot.integration.webclient.WebClientRunner`: Playwright-раннер для веб-клиента 1С:Предприятие 8.3 (авторизация, ожидание готовности интерфейса 1С, действия `open_url`, `click`, `fill`, `wait`, `assert_text`, `assert_section`, фиксация скриншотов). При создании suite предложения проходят структурную проверку поддерживаемых действий и обязательных полей до сохранения; сгенерированные планы не могут содержать `open_url` (вход выполняет исполнитель), а раннер перед любой такой навигацией дополнительно сверяет origin с `web_url` проекта и блокирует переход на другой origin.
4. `testpilot.impact.v8_container.V8Container` и `testpilot.impact.binary_adapter.Binary1CAdapter`: чтение составных файлов 1С v8 (.cfe, .epf, .erf, .cf) — заголовок, каталог, блоки и Deflate-потоки. Директивы расширений (`&Вместо`, `&Перед`, `&После`, `&ИзменениеИКонтроль`) и обращения к метаданным извлекаются только из потоков, распознанных как исходники BSL; при отсутствии таких потоков версия модели не создаётся (статус `metadata_only`), а аудит возвращает `status: no_bsl_modules` с `passed: false`. Разбор контейнеров реальной платформы с модулями подтверждён только на синтетических контейнерах в тестах: на пустом CFE платформы извлекаются лишь служебные потоки без BSL.

*Примечание по проверке:* Адаптеры проверены модульными тестами; полный набор `pytest tests/` в контейнере проходит (единственный пропуск — проверка `docker compose`, недоступного внутри контейнера). Доступ к живой публикации проверен на физической базе DemoEnterprise20.

## Форма входа веб-клиента (подтверждено зондом)

Данные получены read-only зондом `POST /api/v1/ai/connection/probe-login` с `boot=true` 2026-11-17
(`credentials_sent=false`: поля не заполнялись, кнопки не нажимались; зонд лишь открыл страницу, разрешив
странице самой выполнить свои запросы к тому же origin).

- Страница публикации после навигации: `/DemoTrd/en_US/` (внутри контейнера адрес публикации —
  `host.docker.internal:8088`, потому что `localhost:8088` из контейнера недоступен).
- Поле логина: `#authWindow_basic_login` (`name=login`, `type=text`).
- Поле пароля: `#authWindow_basic_password` (`name=password`, `type=password`).
- Кнопка входа: `#authWindow_basic_okButton`.

Раннер использует эти селекторы первыми и ищет форму по всем фреймам: в этой публикации форма была в верхнем
документе, но у других конфигураций она может оказаться в iframe. Появление формы ожидается
`TP_1C_LOGIN_WAIT_SECONDS` (5…120, по умолчанию 25), потому что публикация отдаёт её примерно через 15 с.

Оговорка: id относятся к конкретному релизу платформы и разметке публикации. В других версиях они могут
отличаться — проверяйте зондом (`probe-login`, при необходимости `boot=true`), а не на глаз. Живой вход с
учётными данными этим зондом не проверялся: он не отправляет логин и пароль.
