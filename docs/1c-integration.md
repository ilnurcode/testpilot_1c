# Подключение реальной 1С — следующая стадия

Сейчас работают собственные Python-алгоритмы на нормализованном JSON. Пользователь сообщил о наличии тестовой базы с веб-клиентом и OData, но адреса и учётные данные для подключения ещё не предоставлены. Подтверждённого доступа из этой среды, реальных XML/EDT-выгрузок и запущенных Vanessa Automation / BSL Language Server пока нет. Совместимость с их форматами не заявляется. Методам неподдерживаемых адаптеров соответствует явный NotImplementedError.

1. Получить разрешённую обезличенную выгрузку двух версий одной конфигурации и точную версию платформы/EDT. Согласовать стабильный ID и правила переименования/удаления. Зафиксировать лицензионный доступ к инструментам.
2. Реализовать `ConfigurationAdapter.parse(bytes)->Configuration` на проверенных образцах. Для XML запретить DTD/внешние сущности, ограничить размеры и вложенность. Не выполнять код модулей. Сверить эталонные узлы/связи с экспертом в EDT.
3. Получить образец результата конкретной версии BSL Language Server. Реализовать `ProgramDependenciesAdapter.extract(modules)->list[Edge]`: соответствие символов object_id, тип связи, source/target, origin и confidence. Проверить вызовы, динамические случаи, циклы и недостающие модули. Динамические связи не объявлять доказанными.
4. Загрузить реальный каталог тестов с теми же object_id, экспертно подтвердить привязки и совместимость версий. Импортировать обезличенную историю, отделив её от synthetic; откалибровать веса, время и ML-порог на временной отложенной выборке.
5. Развернуть отдельный исполнитель в разрешённой среде 1С/Vanessa. Согласовать аутентификацию и защищённые endpoints; секреты передавать через среду/менеджер секретов. Никогда не включать команды изменения конфигурации из недоверенного JSON.
6. Исполнитель получает `POST /api/v1/plans/{id}/execution-jobs` после экспертного подтверждения. Контракт содержит ID задания/плана, конфигурацию, версию, тесты и параметры. Сам MVP ничего не запускает.
7. Реальный runner отправляет `POST /api/v1/execution-results`: execution_job_id плюс run со всеми ожидаемыми test_id, временными метками, status, duration_seconds, error и HTTPS-ссылками на артефакты. Неизвестные/недостающие ID и несовместимые версии отклоняются, повтор идентичен — идемпотентен, изменение зафиксированного отчёта — 409. Ссылки сохраняются как строки, сервис их не скачивает.
8. Проверить на живой стендовой базе полный цикл, ошибки/таймауты, права, резервное копирование и согласованные нагрузочные ориентиры. Только после этого утверждать совместимость и качество интеграции.

Контракты: `contracts/execution-job-1.0.schema.json`, `execution-report-1.0.schema.json`, `test-run-1.0.schema.json`. Поле `executor_connected=false` остаётся честным статусом данного MVP даже после импорта вручную присланного отчёта.

Уточнённый целевой процесс с расширениями и Playwright — [connected-workflow.md](connected-workflow.md). Добавленная CLI-диагностика `python -m testpilot.integration.probe` проверяет только публикацию; она ещё не является исполнителем тестов.
