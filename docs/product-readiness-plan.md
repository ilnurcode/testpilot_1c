# TestPilot: план доведения до готового продукта

Статус: утверждён пользователем, исполнение начато (A1). Цель по прямому уточнению пользователя — только TestPilot; 1c-consultant/NewAgent и мост к нему вне scope. Исходный code baseline `ebe4a43`; это ревизия чтения, не подтверждение текущей БД или runtime. Прежние зелёные тесты не доказывают готовность релиза.

## 1. Результат и границы

Поддерживаемый сквозной путь: установка → проект → импорт пользовательского образца → аудит с доказательствами → impact → валидный план с ожидаемыми результатами → явное утверждение → предварительная проверка → разрешённый прогон на тестовой 1С → фактические сравнения → evidence/отчёт → повтор → обновление/резервное копирование/восстановление без потерь.

Целевая среда первого готового релиза на утверждение: существующий локальный Windows-развёртываемый TestPilot, PostgreSQL и 1С 8.3 — предварительное предположение о целевой совместимости, а не подтверждённая версия стенда. Точная платформа/конфигурация/форматы и способы установки фиксируются в матрице до реализации; изменение утверждённой матрицы требует решения владельца. Это не гарантия всех конфигураций/платформ и не SaaS с многоарендностью. Уже заявленные способы установки/форматы не исключаются молча: каждый получает проверяемый статус поддержки. Если требуется сетевое размещение — это явный отдельный профиль с TLS и моделью доступа, не открытие localhost наружу по умолчанию.

**Матрица поддержки перед реализацией.** Ни одна строка сейчас не считается PASS: это предварительные требования и будущие gates доказательства; точные доступные версии выясняются безопасно, без подключения к 1С до допуска. При утверждении плана владелец утверждает состав этой матрицы. Это prerequisite раздела 1 для A1/B1/C2, а не отдельная задача A0.

Моки/синтетика доказывают только локальный контракт. Недостающие доступ/ключ/образец помечаются BLOCKED, а не PASS/SKIP ради зелёного релиза. Не обещаем отсутствие любых будущих ошибок. Старые утраченные данные не объявляем восстановленными; форензика/чистка пользовательских данных не входят в исправления автоматически.

## 3. Общие контракты и запреты

Единственный источник схемы — версии миграций. Источник результата теста — типизированная проверка expected/actual, не HTTP 200, не ответ модели «done» и не клик. Контракт case задаёт действие, параметры, проверку, ожидаемый результат, риск мутации и ссылки на исходный объект/замечание. Контракт run содержит идентификатор попытки, версию утверждённого плана, target identity без секретов, состояние, времена, результаты и ссылки на evidence. Состояния должны различать успех, расхождение, ошибку инфраструктуры, отмену и прерывание; повтор сохраняет прошлую попытку.

Модель предлагает план, но не исполняет произвольный код и не расширяет свои полномочия. Изменение утверждённого плана отзывает утверждение. Секреты не передаются в LLM, отчёты, логи, тестовые фикстуры, git и дистрибутив; удалённые запросы с исходниками требуют согласия.

Во время реализации не использовать рабочую БД для тестов; не менять `.env` и пользовательские секреты; не удалять suites/projects/evidence; не делать автоматических downgrade/revert рабочей схемы; не запускать 1С по общему «продолжай». Любое изменение владельческой схемы/обновление runtime — отдельный согласованный шаг после проверенного бэкапа. План не разрешает push/публикацию/установку зависимостей без согласия.

Контекст: `docs/acceptance.md`, `docs/handoff.md`, `README.md`, `CHANGELOG.md`, CI. Исполнитель: независимый reviewer good + fast-проверки. После A–C, D1.
AC/Verify: исправления подтверждены минимальными регрессионными тестами поведения; полная приёмка на изолированном стенде и реальный пакет зелёные; backup→restore→start повторён на выпускной версии; список поддерживаемых версий/форматов/ограничений точен; нет открытых блокирующих дефектов и секретов в поставке; отчёт указывает фактически выполненные проверки и BLOCKED без ложного «всё работает». Не добавлять бесконечные косметические guard-тесты и побочные функции.

## 5. Организация выполнения и точки допуска

Каждый этап: воспроизводимый дефект/контракт → минимальное изменение → узкая проверка → документация → независимый review. Общие файлы БД/API/Compose меняет один исполнитель; независимые проверки/документация могут идти параллельно. Механика на fast, архитектура/безопасность/сложные дефекты на good; директор проверяет исходники и доказательства. Не создавать второго runner, второго механизма хранения или общий plugin framework без необходимости.

Сейчас допускается только этот план. До изменения кода владелец подтверждает план/границы целевого релиза. Перед реальной 1С отдельно требуются адрес конкретного тестового стенда, допустимые операции и образцы; прошлые пароли/«продолжай» не считаются санкцией. Перед сетевой LLM-приёмкой ключ задаётся владельцем безопасно локально и отдельно согласуется передача входных данных. Перед рабочей миграцией — подтверждение проверенного backup/restore и отдельный допуск. Отсутствие ключа/образца не мешает безопасным кодовым задачам после утверждения плана, но не позволяет объявить весь продукт принятым.
