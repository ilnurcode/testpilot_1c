# Библиотека файлов и история версий

## Работа в интерфейсе

1. Откройте «Проекты и файлы» и создайте проект: название и необязательное описание. Один проект может содержать несколько компонентов одной конфигурации.
2. Перетащите файл в область загрузки или выберите его на компьютере. Укажите тип разработки, имя компонента и необязательное название версии.
3. Оставьте автоматический выбор предыдущей загрузки либо явно выберите базовый файл. Сравниваются только файлы одного проекта, типа и компонента. Можно выбрать полный анализ без базовой версии.
4. Нажмите «Сохранить файл». Загрузка показывает прогресс; исходный файл, метаданные и контрольная сумма сохраняются в PostgreSQL одной транзакцией.
5. В истории можно скачать исходные байты, посмотреть статус или выбрать файл для анализа. Обновление страницы восстанавливает проект по URL вида `#projects/{id}`.
6. Для разобранной JSON-модели доступны полный анализ и сравнение. Результаты сохраняются в истории проекта, экспортируются и могут передаваться в подбор тестов из существующего каталога.

Сохранение и разбор — разные операции. «Ожидает разбора» не означает успешного анализа или тестирования в 1С. Внешняя нейросеть через API и исполнитель 1С ещё не подключены; их статус показан отдельно.

## Форматы и ограничения

| Файл | Сохранение | Анализ сейчас |
|---|---|---|
| Нормализованный JSON контракта 1.0 | До 8 МиБ | Валидация, граф, полный/дифференциальный анализ |
| ZIP с `configuration.json` в корне | До 64 МиБ, JSON до 8 МиБ | Та же валидация и анализ извлечённой модели |
| ZIP с иными исходниками | До 64 МиБ | Сохраняется; нужен проверенный адаптер формата |
| CFE / CF / EPF / ERF / DT | До 64 МиБ | Исходные байты сохраняются; автоматический разбор/восстановление/установка не выполняются |

ZIP не распаковывается на файловую систему. Проверяются пути, дубликаты, символические ссылки, шифрование, лимит 5000 записей и 128 МиБ суммарного объявленного размера. Небезопасный или повреждённый ZIP отклоняется. Поддержка хранения бинарного файла не доказывает, что он является корректным файлом 1С: его внутренний формат пока не проверяется.

В JSON требуется устойчивый configuration_id. Первый нормализованный файл связывает проект с конфигурацией; другие configuration_id в этом проекте отклоняются. Одна конфигурация связывается с одним проектом, а несколько разработок группируются компонентами. Отдельный файл CF сам по себе пока не дополняет граф JSON контекстом типовой конфигурации: нужен адаптер и согласованный снимок модели.

## Версии и идемпотентность

- Каждый новый файл получает порядковый номер внутри проекта и отдельный ID. Без названия версии используется «Загрузка N».
- SHA-256 вычисляется по оригинальным байтам. Идентичные байты в том же проекте, типе и компоненте возвращают существующую загрузку с `idempotent=true`; исходное название/база не перезаписываются.
- Такое же имя версии с другими байтами даёт 409. Другие данные нормализованной конфигурации под прежним номером версии тоже дают 409. Пользователь должен явно выбрать новое название/номер.
- Автоматическая база — последняя существующая загрузка того же типа и компонента. Если она не разобрана, сравнение блокируется с объяснением; можно выбрать более ранний готовый файл или полный анализ.
- Выбор другой базовой версии при анализе не изменяет ранее сохранённый файл или старые отчёты.
- Первый анализ без базы использует пустой исходный граф и включает все объекты загруженной модели. Экспорт содержит маркер `base_version=__no_previous_version__`, параметры `mode=full`, а `impact_analyses.base_id=NULL`. Это явно отмеченный первичный анализ, а не найденные изменения относительно неизвестного прошлого.
- Загрузка по проекту сериализуется PostgreSQL row lock. Синхронная работа с БД выполняется в worker thread, чтобы ожидание блокировки не блокировало ASGI event loop. Совпадающие конкурентные запросы создают одну загрузку.

Полный анализ охватывает загруженную модель. Зависимости типовой учитываются только при их наличии в модели; автоматическое извлечение из реальной типовой конфигурации пока отсутствует.

## Хранение и доступ

Исходные файлы хранятся как BYTEA (`LargeBinary`) в `impact_uploads`; они сохраняются вместе с PostgreSQL volume и резервной копией БД. Списки файлов не читают содержимое BYTEA: поле загружается только при скачивании. Нужны регулярные резервные копии и достаточное место в PostgreSQL. Не удаляйте volume при обновлении сервиса.

Миграция `0003_projects_uploads` добавляет проекты, файлы и связи отчётов. Предыдущие версии/анализы остаются без изменений. Откат миграции запрещён при наличии полных анализов без базы, чтобы не стирать пользовательские отчёты ради изменения схемы.

Все запросы авторизованы. Analyst и expert создают проекты, сохраняют файлы и запускают анализ; runner имеет доступ к чтению. Текущая аутентификация использует общие роли, а не персональные аккаунты: это общая рабочая область команды, не изолированное multi-tenant хранилище каждого физического пользователя. Автор фиксируется как роль в записи и аудите.

## API

- `POST /api/v1/projects`: `{name, description}`.
- `GET /api/v1/projects`: карточки проектов и счётчики.
- `GET /api/v1/projects/{id}`: история файлов и анализов.
- `POST /api/v1/projects/{id}/uploads?filename=...&kind=extension&component=...&label=...&baseline_id=auto`: тело — исходные байты, Content-Type application/octet-stream. `baseline_id`: auto / none / ID существующего файла.
- `GET /api/v1/projects/{id}/uploads/{upload_id}/download`: файл с Content-Disposition attachment, nosniff и X-Checksum-Sha256.
- `POST /api/v1/projects/{id}/uploads/{upload_id}/analyze`: `{baseline_id: "saved" | null | "id", max_depth: 10}`. `saved` использует базу загрузки, null — полный анализ.

Web использует эти публичные API через существующий gateway. Нельзя получить файл другого проекта, подставив его ID в URL текущего проекта.
