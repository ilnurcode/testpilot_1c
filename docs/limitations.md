# Ограничения MVP

- Рабочий импорт — только собственный нормализованный JSON 1.0. Реальные 1С/EDT XML, BSL LSP, OData и Vanessa не реализованы и не проверены. Фактические HTTP/Playwright-проверки доступны только для отдельного синтетического стенда presentation-sales; исполнитель реальной 1С не подключён. Статусы определяются фактическими результатами.
- Только поддерживаемые статические типы связей. Неизвестные, динамические и внешние связи исключаются с предупреждением. confidence не является эмпирически доказанной точностью.
- Сохраняются кратчайшие объяснения: до 3 на пару источник/объект, до 20000 на анализ. Глубина до 100. UI рисует ограниченный граф целевой версии; удалённые узлы и их базовые пути доступны в отчёте. Автоматического полного force-layout больших графов нет.
- Входы максимум 8 МиБ, 10000 объектов, 50000 рёбер. Глубокие/широкие производственные выгрузки потребуют фоновых операций и другого транспорта. Импорт/расчёты синхронные; очереди и SLA конкурентных больших задач не реализованы.
- Точный оптимизатор ограничен 18 необязательными кандидатами с покрытием; далее жадный метод может пропустить выполнимый лучший набор. Конфликт жадного метода не является доказательством математической невыполнимости.
- При отсутствии покрытия процент — 0 с конфликтом. Доступное покрытие может быть 100%, а покрытие всей зоны ниже: оба знаменателя отображаются явно.
- Статистика берётся по всей сохранённой совместимой истории одного configuration_id и synthetic-признака. Нет настраиваемого временного окна, импорта CSV, локализации машинных enum-кодов JSON или конструктора тестов drag-and-drop. Исторические редакции каталога и закрытий дефектов не моделируются.
- Локальный ML оставлен в архивном сценарии и не участвует в новом процессе внешней нейросети. ML технически обучается и проверяется, но пригодность на реальных проектах не доказана. При недостатке истории/классов/качества используется явный fallback. Нет drift-мониторинга, подбора гиперпараметров и оценки причинности.
- HTTP Basic и три общие роли подходят локальной демонстрации. Нет персональных пользователей, SSO, распределённых прав, защиты от подбора паролей или промышленного TLS-терминатора. Для общего доступа нужны HTTPS и дополнительные меры эксплуатации. Аудит фиксирует роль, а не индивидуального сотрудника.
- Миграции/данные двух сервисов разделены таблицами и ревизиями, но используют одну БД и одну роль PostgreSQL. Для усиленной изоляции нужны отдельные DB-роли и grants. Удаление теста — архивирование ради сохранения истории.
- Планы и задания фиксируют снимки расчёта; ручное изменение каталога после подтверждения может потребовать нового плана. Перед экспортом задания проверяется активность/совместимость; нет distributed locking между каталогом и внешним runner.
- Бенчмарк синтетический и ограниченный, не подтверждает производственные SLA или универсальное сокращение времени на 20%.
- В данной cloud-среде обычный Docker build не разрешает внешний DNS. Подготовлен и проверяется offline-вариант с заранее скачанными wheels; сетевой Dockerfile для обычной среды не считается проверенным успешной offline-сборкой.


Библиотека файлов принимает исходные CFE/CF/EPF/ERF/DT и ZIP до 64 МиБ на хранение. Это не добавляет совместимость их парсинга: доступны только нормализованный JSON и JSON-манифест в ZIP. Общая рабочая область использует роли; индивидуальная изоляция физических пользователей пока не реализована. Подробнее — uploads.md.
